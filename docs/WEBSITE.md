# Public website and workspace routes

The product website is generated by Hugo at `https://www.visualnerve.com/`. The production editor has one entry at `https://app.visualnerve.com/`. The former website `/app` path redirects there with HTTP 308 without forwarding query data; `/app` on the isolated app returns HTTP 404. Production builds remove the old shell. Local development/staging test builds may retain `/app/`, explicitly outside the production package. Browser records belong to their original origin: retirement never deletes, moves or encrypts old work. Restore an existing backup or transfer explicitly; preserve an unexported older browser profile and ask `hello@visualnerve.com` before clearing it.

## Pages and content

- `/`: positioning, device screenshots, an editable kiosk example, four infrastructure capacity templates, a Roblox Game Builder entry and product entry points.
- `/features/`, `/use-cases/`, `/process-simulator/`, `/mcp/`, `/developers/`: English, source-verified capabilities and workflows.
- `/privacy/`, `/security/`, `/license/`: data flows, trust boundaries and licensing.
- `/help/`: 26 task guides with search and actual screenshots.
- `https://app.visualnerve.com/`: the encrypted native editor, mandatory browser-storage consent and optional local integration.
- `/api/docs/`: bundled reference, with no Analytics or consent scripts.

Public product pages use `layout: product`. Shared site metadata, navigation, footer and responsive styling live in `hugo/layouts/partials/` and `hugo/static/site/`. Help and the editor keep compact native navigation. The website uses the same saved Appearance; System is the default.

Every page uses the native orange command-symbol logo. Public product navigation is floating; the native workspace, Help and API reference retain their compact header and divider.

The production homepage demo link `https://app.visualnerve.com/?demo=kiosk` creates the bundled kiosk template using the same authoritative template path as New diagram. It runs only after required storage acceptance. A successful local save removes the parameter to prevent duplicate diagrams on reload. No user model is supplied through a URL.

## Consent and Analytics

Klaro 0.7.21 is pinned, locally bundled and retains its BSD-3-Clause license plus bundled component notices. `scripts/consent-assets.mjs` reproduces vendor files from installed dependencies; no CMP CDN request is needed. The build records licenses.

Set repository variable `GOOGLE_ANALYTICS_MEASUREMENT_ID` to the real GA4 Measurement ID. Deploy workflows pass it as `HUGO_PARAMS_GOOGLEANALYTICSMEASUREMENTID`. The configured project ID is `G-1P74HBXS87`; it is a public identifier, not an access secret.

Explicit, default-off consent is required before the Google tag loads. Basic gating sends no denied-mode pings. Exactly nine public page routes are eligible. Editor, Help and API docs never load the tag, including after consent elsewhere. Only sanitized origin/path and a fixed title are supplied; queries, fragments, referrers and workspace content are excluded. Ordinary Google request metadata remains external.

**Disable Enhanced Measurement in the GA4 web data stream before activating the property.** Remove Connected Site Tags or custom automatic tags/events that read page URLs or DOM content. These account-level settings cannot be inspected or changed using a Measurement ID alone. The integration disables Google signals and ad personalization, denies all advertising storage and sends its own page_view. Do not add Tag Manager tags, enhanced-measurement events or custom events reading app DOM, content or URL queries.

Cookie settings provides equal acceptance/rejection and withdrawal. Choices live in two localStorage keys for up to 30 days, separately from IndexedDB storage consent. Withdrawal disables the loaded tag, clears accessible analytics cookies and reloads the page; it cannot retract earlier network requests. Without a configured ID, no tag runs and the settings control explains that no optional analytics is configured.

The app's required local-storage acceptance is independent of optional website tracking. Site consent is not imported/exported with workspace backups.

## SEO and environments

`SITE_URL` sets Hugo's absolute base URL. `HUGO_PARAMS_ENVIRONMENT` is `staging` or `production`. The default build is staging at `https://visualnerve.caripson.com/`, with noindex/nofollow and a robots exclusion for all paths.

Production uses `https://www.visualnerve.com/`, unique topic titles and descriptions, self-canonical URLs, explicit Open Graph/Twitter previews and a generated sitemap for its 36 indexable pages, including all 26 Help guides. Preview metadata identifies the actual 1200×675 WebP and permits large search image previews. The homepage title describes diagrams, data and process simulation while the visible product heading retains its positioning.

Production pages emit a linked JSON-LD graph for `WebSite`, `WebPage` and the real navigation hierarchy as `BreadcrumbList`. The homepage also describes `SoftwareApplication` with its free web-app offer and MPL-2.0 license. No ratings, reviews, publication dates or translated page URLs are invented. This is descriptive schema; Google's [software-app rich-result requirements](https://developers.google.com/search/docs/appearance/structured-data/software-app) also require a genuine rating or review, so this markup does not promise that result. [Site names](https://developers.google.com/search/docs/appearance/site-names) and [breadcrumbs](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb) use Google's separate supported structures.

The workspace remains noindex and is excluded from the sitemap; robots also excludes workspace and command endpoints. Staging emits no search schema. The isolated app reconstructs its private heads, retains no public JSON-LD and blocks indexing with both HTTP headers and robots. The static API reference intentionally remains noindex. Public documentation has no imported user content, and the English documentation has no alternate-language URLs merely because the app interface has eight languages.

The static bundle audit allows only named website pages, curated screenshots, pinned assets and licenses. No workspace backups, user exports or database files are uploaded. Deployment remains manual; see [deployment gates](DEPLOYMENT.md).

## Icons and image delivery

The root `/favicon.ico` contains the native mark at 16, 32, 48 and 256 pixels. `/favicon-96x96.png` is a transparent square PNG and `/apple-touch-icon.png` is an opaque 180-pixel home-screen icon. Website, app, Help, API and error heads declare the same icons. `scripts/site-icons.mjs --check hugo/static` checks PNG checksums, dimensions, ICO frames and provenance against `site/mark.svg` during the normal build; icon generation is a separate explicit maintenance command. The isolated app includes these icons in its audited package and accepted-storage offline shell. The root paths stay stable for crawlers. See Google's [favicon requirements](https://developers.google.com/search/docs/appearance/favicon-in-search).

The four homepage device previews have smaller native WebP variants in both appearances, with width descriptors and responsive `sizes`. Original full-size captures remain available. The opt-in screenshot suite regenerates the variants through the local WebP tools; normal builds use the checked-in images. Appearance selection applies to the complete responsive source sets, including a manually saved theme.

After Hugo, `scripts/fingerprinted-assets.mjs` copies the curated website/device/Help images to content-addressed filenames using the first 16 hex characters of SHA-256. It rewrites rendered HTML paths, including responsive candidates, theme attributes, full-size links and social preview URLs. Original paths remain available as legacy aliases. The static upload audit only accepts a fingerprinted file when its bytes match both the hash and an explicitly allowed original. Offline inventory and isolated Help packaging include the same files; no private workspace records enter this pipeline.

The service worker precaches each verified image once. A request for its original alias can reuse that cached copy, including offline, without downloading or storing the same bytes twice. Previously opened Help pages can retrieve their known older fingerprinted images from retained static caches belonging to the same surface. The production audit removed 177 duplicate precache requests and 7,253,709 image bytes; its core inventory contains 392 files totaling 18,909,817 bytes, excluding optional on-demand voice models.

Deployment publishes verified fingerprinted images with `Cache-Control: public,max-age=31536000,immutable`, before the HTML that references them. A changed image receives a changed address. Mutable aliases, root icons, CSS/JS entry points, HTML and `sw.js` retain `no-cache` revalidation. These directives do not clear IndexedDB. The existing production CloudFront policy allows Brotli/gzip and a one-year maximum TTL, with a one-second minimum even on revalidated files; infrastructure is inspected separately from publication.

The generated `openapi.yaml` contains JSON, a valid YAML subset. Both upload scripts explicitly publish it as `application/json`, permitting the existing CloudFront compression policy to compress it. The endpoint, content and consumers remain compatible. The previous `application/yaml` response transferred the approximately 2.5 MB contract without compression. Full Swagger parsing/rendering can still be expensive on slower phones; changing transfer MIME does not eliminate that browser work. See AWS's [compression conditions and MIME types](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/ServingCompressedFiles.html).

## Core Web Vitals verification

Use cold browser profiles and real HTTPS for production measurements, and isolated synthetic fixtures for local browser regressions. Record viewport, CPU/network throttling, Chrome/Lighthouse versions, consent state and whether caches were cold. Verify LCP and CLS directly; Lighthouse TBT is a laboratory responsiveness proxy, not INP. Keep functional menu/keyboard tests alongside timing observations. Do not add app or documentation tracking to obtain these measurements.

Good Core Web Vitals thresholds are LCP ≤2.5 seconds, INP ≤200 milliseconds and CLS ≤0.1 at the 75th percentile of field visits, assessed separately for mobile and desktop. A green laboratory report cannot establish that the GSC field report passes. GSC uses accumulated visitor data and can take time to reflect a release. See [Core Web Vitals](https://web.dev/articles/vitals) and [the Search Console report](https://support.google.com/webmasters/answer/9205520).

The 2026-10-13 audit used Chrome 155.0.8059.40 and Lighthouse 13.5.0 in disposable profiles, with analytics declined. The public HTTPS homepage scored 95 performance / 100 accessibility on mobile (LCP 2.085 s, CLS 0, TBT 182 ms) and 100 / 100 on desktop (LCP 540 ms, CLS 0, TBT 0). Repeated mobile cold loads at 390×844, 4× CPU slowdown, 1.6 Mbps and 150 ms latency observed LCP 1.00–1.52 s, CLS 0 and menu event durations 80–120 ms. Those observed event durations are not a field INP score.

The controlled before/after preview transferred 270,284 → 25,790 bytes for the four mobile device screenshots, a 90.5% reduction. Median observed LCP was 860 → 932 ms, with CLS 0 in both versions: this comparison establishes fewer image bytes, not an LCP improvement. Concurrent build/test work adds timing noise. Loaded Help and API reference accessibility scans found no violations after the breadcrumb and landmark fixes. Full Swagger parsing remains a documented mobile cost, independently of its corrected transfer MIME. Recheck production after an approved publication and then consult GSC field data; these local changes have not themselves updated that report.
