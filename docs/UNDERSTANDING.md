# Understand, review and explain a diagram

All five workflows use the same canonical objects and relationships. They run locally in the browser, use IndexedDB for saved content, and are available through REST/MCP. Open **Understand** in the toolbar or **More tools** on smaller screens.

## Semantic overview

**Understand → Semantic overview → Summarize related objects** groups related content using diagram hierarchy, tags and retained source information. Choose another grouping when needed. Summary cards show counts and status; connections keep their relationship type, direction and original connection IDs. Connections within a group remain represented as internal aggregates. Untagged content uses labeled layout areas and stable partitions, which are navigation aids rather than claims about business meaning.

Choose **Overview** in the canvas's Overview controls, then expand groups to reveal detail. Explicit expansion frames the newly revealed cards in 2D and 3D; the canonical layout and saved Details camera stay unchanged. **Back one level** closes the last manually opened branch; **Collapse to overview** closes all saved expansions. In 2D, zooming in also opens progressively deeper groups; semantic magnification is measured relative to a readable initial fit, so a small diagram's summary cards are not forced to an unreadable physical scale. In 3D, click a summary card or its entry in the object list to expand one level. **Details** restores the original editable layout and its pen layer. Summary placement is read-only. Grouping does not replace or delete nodes, descriptions, icons, colors, statuses or relationships. 2D, 3D and visual exports use the same current projection. JSON and Markdown continue to describe the canonical graph.

The compact projection displays at most 2,000 cards and maps every object in its input view back to a summary or detail card. Existing CSV filters and relationship focus still determine that input view. API detail levels change at semantic zoom 0.2, 0.55 and 1.2; requested projection zoom must be greater than zero and at most 10. The browser converts physical 2D magnification to this semantic scale. Expanded group IDs are stable while their membership and grouping stay the same. Do not use `overview-group:…` IDs in ordinary node/edge mutation endpoints. Pen annotations remain available in Details; canonical pen coordinates are not drawn over the different compact layout.

The reproducible [`semantic-overview-v1` benchmark](PERFORMANCE_OVERVIEW.json) contains 10,000 objects and 30,000 typed/directed relationships with fixed IDs and source paths. At semantic zoom 1.5 it renders 65 cards and 393 relationship aggregates while retaining all 10,000 node mappings and all 30,000 edge mappings. Five measured full projections had a 438 ms median on the recorded development machine; this measures the pure projection in Vitest/JSDOM, not browser frame rate or GPU performance. Reproduce from `frontend` with `npx vitest run tests/overview-benchmark.test.ts --reporter=verbose`. A separate regression expands/reveals the complete input and checks that the 2,000-card cap retains every original reference.

REST/MCP: `GET/PUT /diagrams/{id}/overview`; PUT uses exact `{baseVersion,overview:{version:1,enabled,grouping:"auto"|"groups"|"tags"|"source",expanded:[]}}`. Discover groups and original-ID mappings through `GET /diagrams/{id}/overview/projection?zoom=0.1`.

## Questions with source evidence

**Understand → Ask diagram** asks what is downstream or upstream of an object, or how two objects are connected. Choose maximum steps, relationship types and whether to include heuristic/unresolved relationships or retained CSV groups outside the current data view. Answers give a shortest modeled path and evidence for each connection. **Focus related objects** or **Focus this path** narrows the diagram without deleting its content.

Directions and cycles are handled explicitly. Unarrowed associations are excluded from directed paths. Code evidence includes retained file/line and syntax, heuristic or unresolved confidence. SQL evidence includes foreign-key definitions or logical JOIN expressions; CSV evidence identifies generated groups and sources. Manual relationships are reported as user-modeled facts. These are static relationships, not proof of actual runtime impact, execution order or business causality. Complete original code/SQL scripts are not retained after import.

Queries traverse up to 50,000 nodes and 200,000 relationships, at depth 1–64, with pages of 1–100 answers (default 25). Complete result counts and explicit depth/uncertainty warnings are returned. Diagram focus has its own 500-object/2,000-relationship limit; the complete paged answers remain available. A changed graph requires asking again before applying an old result.

REST/MCP: read-only `POST /diagrams/{id}/questions` accepts exact `{startId,kind:"downstream"|"upstream"|"path",targetId?,maxDepth?,edgeTypes?,includeHidden?,includeUncertain?,offset?,limit?}`. A path question requires `targetId`. `GET /diagrams/{id}/evidence?nodeId=UUID` reads retained source metadata. Adding `metricId` and optional `offset`/`disposition=all|included|excluded` explicitly requests a page of up to 100 original and cleaned CSV cells, with contributing/excluded rows and original data-row numbers. Those cells are shared with the requesting integration; ordinary relationship questions and app briefs do not include raw CSV rows.

## Local versions and change review

**Understand → Version history** saves named snapshots, compares one with the current diagram or another snapshot, and restores a reviewed version. Ordinary autosaves do not create history. Source refresh creates a checkpoint before applying changes; restore atomically creates a safety checkpoint of current work first. A stale version or failed checkpoint prevents the replacement.

Comparison covers semantic object, connection, source, settings and calculation changes, plus modeled affected dependencies. Routine camera movements and save timestamps are ignored. Lists are bounded at 500 changes and 2,000 affected node/edge references; complete counts and truncation flags stay visible. Detailed field paths are bounded at 100 per object, with an explicit warning. Modeled affected dependencies are not a runtime guarantee.

Restore preserves IDs and exact saved 2D/3D positions. Shared owner profiles remain current so another diagram's owner registry is not rewound; saved assignments are restored. History is separate from Undo/Redo. There are at most 50 versions per diagram, 1,000 per workspace, 256 MiB of archived content and 32 MiB per structural graph. Unchanged immutable CSV rows are shared between snapshots. Capacity errors preserve work and never silently evict named versions; delete unwanted snapshots explicitly.

Snapshots intentionally retain removed objects and source rows locally until the snapshots or diagram/workspace are deleted. Removing a current CSV source alone does not remove rows needed by history. Full workspace backups include history, sharing current dataset rows within the bundle to avoid duplication; single-diagram exports contain current content. Merge/Replace remap historical references safely. Older backups without history remain supported.

REST/MCP: `GET/POST /diagrams/{id}/history`, POST exact `{baseVersion,name}`; `GET/DELETE /diagrams/{id}/history/{snapshotId}`; `GET …/{snapshotId}/compare?to=current|snapshotUUID`; `POST …/{snapshotId}/restore` exact `{baseVersion}`. Review the comparison and use its `currentVersion` for restoration. Writes need Read + write. Revoking the integration grant or storage consent during snapshot/restore preparation prevents the pending history transaction.

## Storyboards and scenes

Open **Diagram player → Storyboard scenes → Order** to create scenes from the current selection, or start from existing numbered nodes. A scene can contain several nodes and highlighted connections, its own narration, a 2–600 second minimum dwell, a 0–10,000 ms transition, and a captured 2D viewport or 3D camera. Reorder, edit, preview and save scenes. Preview uses the saved scene; save draft changes first. Referenced connection endpoints are included in framing. Narration is independent of node descriptions, and a longer spoken description extends the dwell until the audio finishes.

Choose **Storyboard scenes** as the player's source, then Play, Pause, previous/next, or preview a scene. A captured view requires **Details** (semantic overview off) and its matching 2D or 3D mode. Capture is disabled in Overview, and playback or film export with a saved view explains **Choose Details or use Auto-fit objects**. Select **Auto-fit objects** in the scene editor to frame the same content in either mode or in Overview. Playback and film export use the same scenes, highlighting and smooth camera transitions. Playback temporarily reveals source objects hidden by a semantic overview. 3D movement routes around cards. Closing the player, switching its source, or finishing film export restores the prior selection and overview navigation without changing canonical layout. A completed player walkthrough keeps the final scene visible until it is closed or its source changes. English is the default voice; Swedish is available in Settings. Audio, subtitles and preload retain their existing controls and local voice download behavior.

Storyboards coexist with legacy numbering and are saved at `diagram.settings.storyboard`. Maximum: 1,000 unique scene UUIDs, 100,000 total node/edge references, 20,000 references per field and 12,000 narration characters per scene. IDs must exist in the graph. Node/edge deletion prunes references; import/duplication remaps them. Existing movie limits apply: 1280×720 at 30 fps, 30 minutes and 256 MiB, with explicit errors rather than omitted content. See [speech and presentation](SPEECH.md) and [API](../API.md#numbered-diagram-presentations).

REST/MCP: `GET/PUT /diagrams/{id}/storyboard`; PUT exact `{baseVersion,storyboard:{version:1,scenes:[{id,name,nodeIds,edgeIds,narration,seconds,transitionMs,view?}]}}`. View is `{mode:"2d",viewport:{x,y,zoom}}` or `{mode:"3d",camera:{position,target,up?}}`. Open with `POST /presentation/open` and `{diagramId?,source:"storyboard"}`. `POST /presentation/seek` exact `{index}` previews an existing zero-based step paused. `POST /presentation/video` accepts optional `source:"nodes"|"storyboard"`; omission uses the current player source. Runtime state adds `source,sceneId,nodeIds,edgeIds,title,narration`; legacy `nodeId` is the first scene object and video `nodeIndex` denotes the current step.

## Reviewed app specifications for Lovable

**Build with Lovable** now includes **Review the app specification**. Expand data model, screens/navigation, business rules, proposed API, acceptance criteria and decisions. Add requirements or corrections and answer open decisions. Edits are saved with the diagram and support Undo/Redo. The final brief includes these reviewed additions; copy, download or explicitly open it in Lovable using the existing handoff controls.

Observed SQL schemas and foreign keys are source facts. Candidate screens and read endpoints are labeled design proposals requiring confirmation. Conceptual database objects have unknown fields until defined. Layout, hierarchy and Done status do not imply execution order. Heuristic relationships, missing branch conditions, record identities, authorization, storage, writes and errors become questions rather than invented behavior. Acceptance criteria use declared constraints and descriptions; refine general descriptions into concrete inputs, expected outputs and failure cases.

The draft at `diagram.settings.buildSpecification` is `{version:1,sections:{},answers:{}}`. Six known section keys are `dataModel,screens,businessRules,apiContract,acceptanceCriteria,decisions`; fields have at most 30,000 characters, the total draft 180,000, and answers at most 200 keys. A preview shows at most 200 decisions and counts additional unresolved ones. Narrow the scope to review omitted decisions. Original CSV row values and arbitrary custom metadata remain excluded. Diagram and relationship references in the external text use portable labels.

REST/MCP: `GET/PUT /diagrams/{id}/build-specification`, PUT exact `{baseVersion,specification}`; read-only `POST /diagrams/{id}/build-brief` exact optional `{scope:"diagram"|"selected"|"csv-view",selectedIds,instructions}` returns the full unsent brief and structured specification. Selected scope requires existing node IDs. This endpoint neither publishes nor sends to Lovable.

## Discovery and development

`visual_nerve_api_docs` and its MCP guide/resource advertise these workflows without requiring an external documentation link. The generated [OpenAPI](openapi.yaml) contains the complete schemas. Graph mutations use the latest `baseVersion`; read-only questions and brief previews do not advance it. All integration requests retain local storage consent, MCP grants and 32 MiB transport limits.

Implementation modules live in `overview/`, `questions/`, `history/`, `presentation/storyboard*`, and `export/build-specification*`; shared repository command routing is in `storage/understanding-commands.ts`. Production deployment remains manual through **Deploy S3 → Run workflow** after review.
